# uv integration

The adapter targets uv `46b84fd0bfec23b72f29e8e2185ba68a65052f48`. uv uses
`mailparse` 0.16.1 in two places: distribution metadata in `uv-pypi-types`, and
`WHEEL` headers in `uv-install-wheel`. Both need ordered headers and decoded
values. Resolution ignores the body; publishing retains a UTF-8 description.
uv does not use MIME parts, addresses, attachments, or body transfer decoding.

[The adapter](uv-integration.patch) replaces both dependencies and leaves the
packaging rules in uv: first-value selection, `UNKNOWN` filtering, repeated
fields, WHEEL value trimming, and description fallback. Header spelling remains
unchanged for WHEEL's case-sensitive map. Decoding errors propagate through the
existing metadata and wheel error paths.

To validate the adapter, check out the pinned uv revision into `uv-source` at the
repository root, then run:

```console
python3 scripts/test_uv.py
```

The script checks the revision and hashes the upstream test modules before and
after applying the patch, then runs the `uv-pypi-types` and `uv-install-wheel`
library suites. The original tests are unchanged. Eleven
test functions directly exercise email parsing: two resolution metadata tests,
three full metadata tests, four email-file tests, one wheel-version test, and
one empty-value test. The full suites include unrelated tests too.

Local Linux validation on 2026-10-05 passed all 51 `uv-pypi-types` tests and all
22 `uv-install-wheel` tests, including those eleven parser tests. This validates
the two modified crates; it does not cover uv's complete resolver, publishing,
or network integration suites. The Linux workflow repeats the same pinned test.

## Compatibility

Header recovery follows Python's `BytesHeaderParser(policy=compat32)`. This
intentionally changes some malformed inputs accepted or rejected by mailparse:

- A colonless line or invalid field name starts the body; mailparse can retain
  these as headers.
- Leading continuations are recorded as defects, and lone CR line endings are
  accepted.
- Invalid raw UTF-8 is replaced during explicit value decoding rather than
  interpreted as Latin-1.
- Unsupported encoded-word charsets and invalid Base64 return decoding errors
  rather than silently retaining the encoded text.

These differences can change uv's error category or which fields it sees.
Parser defects are available to callers; the adapter uses Python's recovery
without rejecting defects. The description body remains opaque bytes until uv
validates its UTF-8.

## Fixtures and benchmarks

`tests/fixtures/uv/manifest.json` records archive members, the pinned source
revision, content hashes, and expected raw headers generated by Python. The 48
files contain 20 wheel METADATA files, 20 WHEEL files, and eight PKG-INFO files.
One test wheel contains multiple metadata directories. Black's PKG-INFO provides
a long description: 78,181 bytes total, with 2,088 bytes of headers and separator.
Regenerate from a checkout with:

```console
python3 scripts/update_uv_fixtures.py /path/to/pinned/uv
```

The fixture sources come from uv's test tree; its MIT and Apache licenses and
Black's license are retained alongside them. Archive/member provenance is
preserved for the embedded package metadata.

The `parse` benchmark extracts owned fields used by resolution, publishing, or
wheel installation. Both parsers construct the same outputs, including ordered
duplicates and description fallback. It does not parse PEP 440/508 values or
perform network, archive, or filesystem operations inside the timed region.
Each of the 28 METADATA/PKG-INFO files is read as both resolution and publishing
metadata. Together with 20 WHEEL files and five generated cases, this gives 81
workloads: 31 resolution, 30 publishing, and 20 WHEEL. Generated cases cover
dependency counts, folding, and encoded words. WHEEL extraction uses uv's
`FxHashMap` type on both sides.
Output equality is checked before timing. `--test` checks equality without timing.

```console
cargo bench --bench parse -- --samples 31
cargo bench --bench parse --features benchmark-jemalloc -- --samples 31
```

CSV output includes medians and p10/p90 samples. Runs alternate parser order and
include output destruction. Fixture loading and correctness checks are excluded.
Performance claims require measured results for both allocators.
